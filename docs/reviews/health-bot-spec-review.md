# 健康管理助理規格審查（對 v0.1）

2026-11-12。審查範圍：`docs/health-bot-spec.md` v0.1，以及同分支上的 `muse/health/contracts.py`、`muse/health/tenant.py`、`config/tenants/*.yaml`。本文件不是法律意見。

**總評：** 方向是對的。核心 app 只做使用者委託的健康助理，資料交換預設關閉，再加上授權（mandate）、收據和「沒有允許的模型就停，不改送別處」，跟設計規劃書 v0.2 的 Part B 對得起來。但 §2「只有使用者打得開」與實際架構矛盾，試點前必須先改；其餘必改項同樣要在規格裡給出具體選擇，不能留給實作時再決定。

發現項以 `HB-xx` 編號，供規格 v0.2 的改動對照。

## 必改（試點前）

### HB-01 —「只有使用者打得開」和架構互相矛盾（高）

對應 v0.1 §2 規則 1、§3 架構圖、§9「公司讀不到內容」。

解密發生在 app 伺服器的記憶體裡，那台伺服器放在醫院（之後是公司）。這樣管理員其實讀得到內容，§2 說「管理員不可信」和 §9 說「公司讀不到內容」就都不成立。

要嘛把解密放到使用者端（瀏覽器 WebCrypto，或裝置上的 app），要嘛把措辭改成「代管單位承諾不讀」，不能兩邊都說。

### HB-02 — 授權可能被助理自己簽出來（高）

對應 v0.1 §5；`contracts.py` 的 `Vault.sign`（Ed25519 金鑰存在保險庫裡）。

保險庫解鎖時助理也拿得到這把金鑰，理論上它能替自己簽授權。`exchange.grant`、`llm.cloud` 這類授權應該要求使用者在場確認（passkey / WebAuthn），而不是只用保險庫金鑰簽。

### HB-03 — 收據「可驗證沒被改寫」只說對一半（高）

對應 v0.1 §2 規則 3、§3（授權簿與收據日誌和保險庫在同一個 SQLite 檔）。

雜湊鏈和保險庫存在同一個檔案，拿得到檔案的人可以整條鏈重寫。要定期把檢查點簽章後送到外部，例如設計規劃書 v0.2 的透明日誌或 EAS，不然要把防護的是哪種威脅寫清楚。另外也要寫明收據本身有沒有加密：時間、模型、紀錄種類這些中繼資料一樣敏感。

### HB-04 — `content_sha256` 是明文的雜湊，沒有加鹽（高）

對應 v0.1 §4「以內容雜湊指稱紀錄」；`contracts.py` 的 `Record.content_sha256` 與 `Receipt.record_refs`。

短紀錄（例如一行檢驗值）可以被人逐一猜測比對出來。收據應該改用以保險庫金鑰做的 HMAC。

### HB-05 — 從醫院搬到公司時，授權不能「跟著走」（高）

對應 v0.1 §3「授權與收據跟著走」。

發行者換了，個資的控制者也就換了，給醫院的同意不能延用到公司。搬家時要重新簽同意書和授權，舊收據只保留作為歷史紀錄。

### HB-06 — 隱私等級有兩套名稱（高）

對應 v0.1 §4；`contracts.py` 的 `Egress`（`none` / `local` / `private` / `cloud`）與授權範圍 `llm.cloud`；`tenant.py` 與閘道的 `x-muse-privacy`（`public` / `standard` / `private` / `local`）。

兩套詞彙沒有對照表，閘道就會從這個落差漏出去。要統一成一張對照表。

### HB-07 — 閘道回報的隱私等級是它自己說的（高）

對應 v0.1 §3「回應若沒有帶著閘道實際執行的隱私等級，就不採用該回應」。

這只防得了設定錯誤，防不了閘道被改。比較好的做法是讓閘道對每個回應簽章（attestation），或把該欄位寫進閘道自己的收據。

## 應改

### HB-08 — 緊急症狀的處理前後不一致

v0.1 §1 說「只做一件事：請立即就醫」，§6 卻說「顯示在回覆最前面」，然後繼續回答。要選一種，而且要有中文的測試集，量出漏判率（false negative）和誤判率（false positive）。

### HB-09 —「來源紀錄裡沒有的數字就攔下」會誤殺參考範圍說明

對應 v0.1 §6。解釋名詞與參考範圍是允許的，但輸出檢查若攔下「來源紀錄裡沒有的數字」，報告上本來就印的參考值會被誤殺。要開白名單。

### HB-10 — 加密規格沒寫

對應 v0.1 §2、§8。沒有寫 KDF（建議 Argon2id 並寫出參數）、加密演算法（XChaCha20-Poly1305 或 AES-GCM）、是整個檔案加密還是逐筆加密、`search()` 的索引放在哪裡。

### HB-11 — 首次使用就自動簽發的預設授權等於預設同意

對應 v0.1 §5。使用者首次使用時就自動簽發的預設授權要明確顯示出來，否則等於預設同意。

### HB-12 — 復原時發行單位持有一份金鑰碎片，代表它有一部分的權力

對應 v0.1 §8「裝置、發行單位協助、信任聯絡人三者取二」。這點要在同意書裡寫清楚。

### HB-13 — `private` 供應商狀態依賴有人讀過條款

對應 v0.1 §3 公司發行欄、`config/tenants/company.yaml`，以及閘道的 `config/providers.yaml`。`private` 是否成立，取決於有人讀過條款後記入政策。要加上審查日期（reviewed-on）和到期／重新檢查期限。

## 法規（需律師，不是法律意見）

### HB-14 — 可能落入 TFDA 醫療器材軟體（SaMD）

「用白話說明個人報告」可能落入 TFDA 醫療器材軟體的範圍，這是試點最大的未知。對應 v0.1 §1、§9。

### HB-15 — 個資法 §6 特種個資

病歷和健檢資料屬於個資法 §6 的特種個資，需要書面同意。

### HB-16 — 醫療法 §72 保密義務

醫院發行時還要看醫療法 §72 的保密義務。v0.1 §9 未列。

### HB-17 — 公司發行後的跨境傳輸與新加坡 PDPA

公司發行後，如果 Ceresus（新加坡）參與營運，就涉及跨境傳輸和新加坡的 PDPA。v0.1 §9 只寫了「公司讀不到內容」，沒有處理跨境。

### HB-18 — 人體研究法

若試點或附加功能涉及研究，要看人體研究法（v0.1 §9 已提到是否需 IRB，應把這條法規寫清楚）。

## 創新建議

### HB-22 — 把保險庫、授權、收據做成可攜的同意錢包（consent wallet）

授權直接對應到 HL7 FHIR Consent 和 GA4GH DUO，以及 ISO/IEC TS 27560 的同意收據，寫進核心機制，不只用在附加功能上。這樣任何醫院都能驗證，也就是設計規劃書 v0.2 收據層真正的產品形態，比助理本身更難被大廠複製。
